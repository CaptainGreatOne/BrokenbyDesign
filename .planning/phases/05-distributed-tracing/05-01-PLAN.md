  <name>Task 1: Create OTel Collector configuration with rich pipeline</name>
  <files>otel-collector/config.yaml</files>
  <action>
Create `otel-collector/config.yaml` with a production-realistic pipeline configuration:

**Receivers:**
- OTLP receiver with both HTTP (0.0.0.0:4318) and gRPC (0.0.0.0:4317) protocols

**Processors (ORDER MATTERS - tail sampling BEFORE batch per research pitfall #5):**
1. `attributes` processor: Insert `deployment.environment=local` on all spans for attribute enrichment
2. `tail_sampling` processor:
   - `decision_wait: 10s`
   - `num_traces: 10000`
   - `expected_new_traces_per_sec: 100`
   - Policies:
     - `errors`: type=status_code, status_codes=[ERROR] (always sample errors)
     - `slow_requests`: type=latency, threshold_ms=1000 (always sample slow)
     - `probabilistic`: type=probabilistic, sampling_percentage=100 (sample everything in dev - learner sees all traces)
3. `batch` processor: timeout=10s, send_batch_size=1024, send_batch_max_size=2048 (AFTER tail sampling)

**Exporters:**
- `otlp` exporter to `jaeger:4317` with `tls.insecure: true` (NOT deprecated Jaeger exporter)

**Service pipeline:**
- traces: receivers=[otlp], processors=[attributes, tail_sampling, batch], exporters=[otlp]

NOTE: Set probabilistic sampling to 100% for the learning environment so the learner sees every trace. In production this would be 10% or lower.

<task type="auto">
  <name>Task 2: Add Jaeger and OTel Collector to Docker Compose</name>
  <files>docker-compose.yml</files>
  <action>
Add two new services to `docker-compose.yml` in the tracing profile:

**jaeger service:**
- Image: `jaegertracing/all-in-one:latest`
- Container name: `jaeger`
- Environment variables:
  - `COLLECTOR_OTLP_ENABLED=true` (enable OTLP receiver)
  - `SPAN_STORAGE_TYPE=badger` (persistent storage)
  - `BADGER_EPHEMERAL=false` (survive restarts)
  - `BADGER_DIRECTORY_VALUE=/badger/data`
  - `BADGER_DIRECTORY_KEY=/badger/key`
  - `BADGER_SPAN_STORE_TTL=72h` (3 days retention matching Loki)
- Ports:
  - `16686:16686` (Jaeger UI)
  - `4317` (OTLP gRPC - internal only, not exposed to host since Collector uses it)
- Volumes: `jaeger-badger:/badger` for persistent storage
- Restart: `unless-stopped`
- Resource limits: `mem_limit: 512m`
- Profiles: [`tracing`, `full`]
- Healthcheck: `wget --no-verbose --tries=1 --spider http://localhost:16686/ || exit 1` with interval 10s, timeout 5s, retries 3
- Networks: default network (same as other services)

**otel-collector service:**
- Image: `otel/opentelemetry-collector-contrib:latest`
- Container name: `otel-collector`
- Command: `["--config=/etc/otelcol/config.yaml"]`
- Volumes: `./otel-collector/config.yaml:/etc/otelcol/config.yaml:ro`
- Ports:
  - `4317:4317` (OTLP gRPC - exposed for services)
  - `4318:4318` (OTLP HTTP - exposed for services)
- Depends on: jaeger (service_healthy)
- Restart: `unless-stopped`
- Resource limits: `mem_limit: 512m`
- Profiles: [`tracing`, `full`]
- Healthcheck: `wget --no-verbose --tries=1 --spider http://localhost:13133/ || exit 1` (Collector health extension) with interval 10s, timeout 5s, retries 3
- Networks: default network

**Also add to OTel Collector config.yaml** the health check extension:
```yaml
extensions:
  health_check:
    endpoint: 0.0.0.0:13133

service:
  extensions: [health_check]
```

**Add named volume:**
- `jaeger-badger:` in the top-level `volumes:` section

**Update resource budget comment** at top of docker-compose.yml to reflect new services:
- Jaeger (512M) + OTel Collector (512M) = ~1GB for tracing profile

**Important:** Add `otel-collector` as a dependency for the 3 application services (web-gateway, order-api, fulfillment-worker) but use `service_started` condition (not service_healthy) so services start even if Collector isn't ready yet. The OTel SDKs handle retry internally. Only add this dependency when the tracing profile is active - use the depends_on with condition pattern matching existing service patterns.

Actually, since Docker Compose profiles mean these services only start with `--profile tracing`, the application services should NOT have a hard dependency on otel-collector. The OTel SDKs will handle connection failures gracefully. Do NOT add depends_on from app services to otel-collector.
