Create `services/web-gateway/src/chaos.js` — the chaos state management module for web-gateway. This module exports:

**1. Chaos State Object (in-memory, resets on restart):**
```javascript
const chaosState = {
  latency: { enabled: false, severity: null, delayMs: 0 },
  errors: { enabled: false, severity: null, errorRate: 0 },
  crash: { enabled: false, severity: null, countdown: null },
  memory: { enabled: false, severity: null, allocations: [] },
  disk: { enabled: false, severity: null, files: [] }
};
```

**2. Severity Presets:**
```javascript
const PRESETS = {
  latency: { mild: { delayMs: 300 }, severe: { delayMs: 3000 } },
  errors: { mild: { errorRate: 0.10 }, severe: { errorRate: 0.50 } },
  crash: { mild: { countdown: 10 }, severe: { countdown: 3 } },
  memory: { mild: { sizeMB: 50 }, severe: { sizeMB: 200 } },
  disk: { mild: { sizeMB: 10 }, severe: { sizeMB: 50 } }
};
```

- `latency` preset `mild` = 300ms delay, `severe` = 3000ms delay
- `errors` preset `mild` = 10% error rate (HTTP 500), `severe` = 50%
- `crash` preset `mild` = crash after 10 requests, `severe` = crash after 3 requests
- `memory` preset `mild` = allocate 50MB, `severe` = allocate 200MB (kept under container 512M limit)
- `disk` preset `mild` = write 10MB to /tmp, `severe` = write 50MB to /tmp

**3. Express Middleware Function `chaosMiddleware(req, res, next)`:**
This middleware runs BEFORE route handlers but AFTER metrics tracking middleware. It MUST skip these paths (no chaos on control/observability endpoints):
- Paths starting with `/chaos`
- Path `/metrics`
- Path `/health`

Middleware logic:
- If `chaosState.latency.enabled`: add artificial delay using `setTimeout(next, chaosState.latency.delayMs)` instead of calling `next()` immediately. Log at WARN level: "Chaos: injecting latency" with `handler: "ChaosMiddleware"` and `delay_ms` value.
- If `chaosState.errors.enabled`: roll `Math.random()` against `chaosState.errors.errorRate`. If triggered, return HTTP 500 with `{ error: "Chaos: injected error", chaos: true }`. Log at WARN level: "Chaos: injecting error response". Do NOT call `next()`.
- If `chaosState.crash.enabled`: decrement `chaosState.crash.countdown`. When countdown reaches 0, log at ERROR level: "Chaos: service crash triggered", then call `process.exit(1)` after a 100ms delay (to allow log flush).
- If latency is enabled but errors are not triggered, call `next()` after the delay.
- Order of checks: crash countdown first (always decrement if enabled), then errors (may short-circuit), then latency (wraps next()).

**4. Express Router `chaosRouter` with these endpoints:**

**POST /chaos/enable** — Enable a chaos scenario
Request body: `{ "scenario": "latency|errors|crash|memory|disk", "severity": "mild|severe", "params": { ... optional overrides } }`
- Validate scenario is one of the 5 types
- Use severity preset values, override with params if provided
- For `memory`: allocate Buffer(sizeMB * 1024 * 1024) and push to chaosState.memory.allocations array
- For `disk`: write random data to `/tmp/chaos-{uuid}.dat` and push path to chaosState.disk.files array
- For `crash`: set countdown (from preset or params.countdown)
- Log at WARN level: "Chaos: scenario enabled" with scenario, severity details
- Return 200 with `{ status: "enabled", scenario, config: { ...active config } }`

**POST /chaos/disable** — Disable a specific chaos scenario
Request body: `{ "scenario": "latency|errors|crash|memory|disk" }`
- Reset that scenario's state to defaults (enabled: false)
- For `memory`: release allocations (set array to [])
- For `disk`: delete created files, clear array
- Log at INFO level: "Chaos: scenario disabled"
- Return 200 with `{ status: "disabled", scenario }`

**POST /chaos/reset** — Reset ALL chaos scenarios
- Iterate all scenarios and reset to defaults
- Clean up memory allocations and disk files
- Log at INFO level: "Chaos: all scenarios reset"
- Return 200 with `{ status: "reset", message: "All chaos scenarios disabled" }`

**GET /chaos/status** — Get current chaos state
- Return 200 with the full chaosState object (excluding internal arrays for memory/disk, just show enabled/severity/size info)

Import the logger from `./logger` for chaos logging. Use `handler: "ChaosMiddleware"` in all log entries.

Export: `{ chaosMiddleware, chaosRouter, chaosState }`

Modify `services/web-gateway/src/server.js` to integrate the chaos module:

**1. Import the chaos module** at the top (after existing imports):
```javascript
const { chaosMiddleware, chaosRouter } = require('./chaos');
```

**2. Mount chaos routes BEFORE the main routes** but AFTER the metrics endpoint. The chaos endpoints need to be accessible without going through chaos middleware. Add this line after the `/metrics` endpoint and before `app.use('/', routes)`:
```javascript
// Chaos engineering control endpoints (mounted before chaos middleware)
app.use('/chaos', chaosRouter);
```

**3. Add chaos middleware AFTER chaos routes but BEFORE main routes.** Insert between the chaos route mount and `app.use('/', routes)`:
```javascript
// Chaos engineering middleware (injects failures into normal request handling)
app.use(chaosMiddleware);
```

The final middleware/route order in server.js should be:
1. JSON body parser
2. Correlation ID middleware
3. Request logging middleware
4. Response timing middleware
5. Prometheus metrics tracking middleware
6. GET /metrics endpoint
7. Chaos routes (POST /chaos/enable, etc.) — not affected by chaos middleware
8. Chaos middleware — affects only routes below this point
9. Main routes (GET/POST /orders, /health, etc.)
10. Error handling middleware

This order ensures:
- Chaos control endpoints always work (no self-sabotage)
- Metrics are always collected (even during chaos)
- Chaos effects apply to business routes
- Logging captures chaos-injected behavior
