<objective>
Add a `service_healthy` Prometheus gauge metric to all three application services (web-gateway, order-api, fulfillment-worker). This metric enables the ServiceUnhealthy alert rule in Plan 03 to detect when a service is running but failing health checks.

Purpose: The ServiceUnhealthy alert distinguishes between "service completely down" (InstanceDown) and "service running but degraded" (ServiceUnhealthy). This requires each service to self-report its health status via a Prometheus gauge.

Output: Each service exposes a `service_healthy` gauge (0=unhealthy, 1=healthy) at its existing /metrics endpoint.
</objective>

**web-gateway (Node.js with prom-client):**

1. In `services/web-gateway/src/metrics.js`:
   - Add a new Gauge metric: `service_healthy` with help text "Service health status (1=healthy, 0=unhealthy)" and no extra labels. Register it on the existing `register`.
   - Export it alongside existing metrics.

2. In `services/web-gateway/src/routes.js`:
   - Import `serviceHealthy` from metrics.
   - On server startup (or first request), set `serviceHealthy.set(1)`.
   - In the existing `/health` endpoint, add logic: check that gRPC client and Redis are reachable (the existing health endpoint already returns 200 — enhance it to set the gauge to 0 if dependencies are down, 1 if healthy). The simplest approach: the health endpoint already reports healthy, so set `serviceHealthy.set(1)` on each successful health response. If health ever returns non-200 (add a try/catch around dependency checks), set to 0.
   - A practical minimal approach: set gauge to 1 at startup. The health endpoint is already called by Docker healthcheck every 5s. Update the gauge in the health handler: try to verify gRPC and Redis connectivity — if both OK set 1, if either fails set 0. Keep the HTTP response the same (200 with status field showing actual health).

**order-api (Python with prometheus-client):**

1. In `services/order-api/src/metrics.py`:
   - Add a Gauge: `service_healthy = Gauge('service_healthy', 'Service health status (1=healthy, 0=unhealthy)')`.

2. In `services/order-api/src/server.py`:
   - Import `service_healthy` from metrics.

The metric will remain at 1 unless explicitly changed (which trigger scripts in Plan 04 can manipulate by pausing dependencies).

If we pause only dependencies (like DB), we can have the health handler check DB connectivity and set gauge to 0 — but this adds complexity. For Phase 4, the simple "set 1 at startup" approach is sufficient. The ServiceUnhealthy alert will fire if a future phase or manual intervention sets it to 0.
